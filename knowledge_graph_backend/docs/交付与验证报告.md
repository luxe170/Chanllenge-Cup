## 3. Docker 集成验证

已在 Docker Desktop 4.86.0、Docker Engine 29.7.2、Compose 5.3.1 上完成真实容器验证：

- `postgres:17-alpine`、`neo4j:5-community`、`migrate`、`api`、`worker` 全部按预期启动；
- 一次性迁移容器成功退出，其他四个长驻服务健康；
- 未携带管理密钥的写请求返回 401；
- 正式 API 创建任务，独立 worker 异步导入真实 CSV；
- worker 停机期间任务保持 `queued`，恢复后自动完成；
- 错误 CSV 使任务进入 `failed`，保留明确错误；修复文件后使用同一任务 ID 重试成功；
- 删除并重建全部容器但保留数据卷后，任务、图版本、PostgreSQL 数据和 Neo4j 投影均保持不变；
- API、worker 和迁移日志未出现未处理异常。

本轮实测发现并修复了三项会影响正式部署的问题：

1. Neo4j 健康检查额外环境变量被误解析为数据库配置，现改为从镜像支持的 `NEO4J_AUTH` 取凭据；
2. API 与 worker 原先可能并发执行 Alembic，且 worker 误用 HTTP 健康检查；现已拆出单次 `migrate` 服务并增加 worker 依赖健康检查；
3. 关闭 SQLAlchemy autoflush 时，首轮运行看不到刚写入的种子别名；现已显式刷新并加入回归测试。

输入：`data/processed/relevant_jobs.csv`

|---|---:|

| 无效输入 | 0 |

从全新空数据卷连续执行两次相同导入，两轮的输入数、技能证据数、聚合关系数、发布关系数和审核关系数完全一致。最终活动版本为 `graph_2026-07-31_fd63419c`。API 的 `skill_reverse` 视图返回其中符合该视图层级的 36 个节点、74 条关系；这是视图过滤结果，与 Neo4j 的完整投影计数不冲突。

新岗位候选数量较多不是“已发现 193 个新岗位”，而是 193 组尚未可靠链接的规范化标题。它们必须结合样本数、来源数、时间连续性、候选技能和人工审核继续合并或链接。系统没有把这些低可信候选直接发布到 Neo4j。

## 5. 当前质量边界

后端已达到可运行、可部署、可扩展的工程骨架和真实数据闭环，但模型质量还取决于团队后续完成以下数据工作：

1. 制作不少于 100 条人工标注 JD；
2. 扩充岗位别名和技能词典；
3. 人工处理高频新岗位候选；
4. 根据 Precision、Recall、F1 调整阈值；
5. 接入受约束的大模型候选抽取器，以发现词典之外的技能；
6. 在 CI 中持续执行容器集成测试，并补充高并发、长时间运行和大数据量压测。

在没有金标准标注集前，不能宣称 JD 解析准确率达到 90%。后端已经提供 `gold_annotations` 和 `/evaluations/extraction`，用于得到可复算的指标。

## 6. 隔离说明

正式交付文件均位于 `knowledge_graph_backend/`。虚拟环境、测试运行目录、字节码缓存、覆盖率数据以及 Docker 故障路径验证文件均位于 `knowledge_graph_backend_temp/`。真实数据目录只读挂载；没有修改现有 `src/`、`frontend/`、`data/` 或团队文档。

验证完成后，项目名为 `career_prism_kg_validation` 的容器、网络、数据卷和应用镜像均已删除；PostgreSQL、Neo4j 和 Python 基础镜像未删除。
