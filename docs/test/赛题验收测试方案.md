# 职涯棱镜赛题验收测试方案

## 1. 目的与验收口径

本方案对应赛题 `XH-202621`，用于验证系统是否完成以下闭环：

```text
多源 JD 采集 -> 清洗去重 -> 技能与岗位抽取
-> 新岗位 / 既有岗位能力变更 / 无变化分类
-> 人工审核 -> 增量更新图谱 -> 前端展示
-> 简历解析 -> 人岗匹配与差距分析 -> 学习路径
```

正式验收必须同时满足：

| 赛题硬指标 | 验收门槛 | 证据 |
|---|---:|---|
| 岗位 JD 测试数据 | 不少于 100 条 | 冻结数据文件、来源清单、标注文件 |
| JD 解析准确率 | `>= 90%` | 字段级 Precision、Recall、F1 报告 |
| 简历提取准确率 | `>= 90%` | 技能实体 micro-F1，另报字段完整率 |
| 人岗匹配准确率 | `>= 90%` | 专家标注岗位 Top-1 Accuracy，另报 Top-3 |
| 单元测试覆盖率 | `>= 60%` | `coverage.xml` 和 HTML 报告 |
| 核心闭环 | 全部通过 | 接口日志、数据库状态、图谱前后快照、页面录屏 |
| 指定交付样例 | 1 个新岗位、1 个既有岗位更新 | 输入 JD、审核记录、图谱输出 |

准确率不能使用系统自己生成的标签评测系统自己。测试集必须由人工标注，并与规则开发、提示词调试使用的数据隔离。

## 2. 当前基线（2026-08-31）

- 原始 JSONL 数据共 8110 条：字节 5387、腾讯 2326、阿里 314、美团 68、华为 4、闭环演示 11。
- 仓库已有 34 个测试方法，但缺少正式人工金标准数据集和三项准确率计算脚本。
- 本机执行 `unittest discover`：发现 27 项，23 项通过、1 项失败、3 个测试模块因缺少 `httpx2` 无法导入。
- 失败项为岗位演化记录数量断言：期望大于 10，实际为 3。该断言依赖当前处理数据，需改成固定夹具后再作为稳定回归测试。
- 当前 `requirements.txt` 未声明 `httpx2`、`coverage`，因此接口测试和覆盖率门槛尚不可复现。
- `使用说明.md` 对部分页面仍标记为 Mock，与当前代码已经接入的 JD 批次、审核、图谱、简历和匹配接口不一致，正式验收前需更新。

因此，目前可以证明部分功能可运行，但还不能证明三项准确率达到 90% 或覆盖率达到 60%。

## 3. 测试数据设计

### 3.1 JD 金标准集

建立 `data/evaluation/jd_gold_120.jsonl`，建议使用 120 条而非刚好 100 条，组成如下：

| 维度 | 数量 | 目的 |
|---|---:|---|
| 人工智能 | 30 | 覆盖大模型、RAG、Agent、算法岗位 |
| 大数据 | 25 | 覆盖数据开发、数据平台、实时计算 |
| 智能系统/机器人 | 25 | 覆盖具身智能、机器人、嵌入式 |
| 物联网 | 20 | 覆盖 IoT 平台、边缘计算、协议栈 |
| 易混淆/噪声岗位 | 20 | 产品、售前、销售、法务、重复与夸张 JD |
| 合计 | 120 | 满足不少于 100 条要求 |

来源至少覆盖 4 家企业、3 个招聘平台和 3 个时间窗口。同一模板的重复 JD 不得跨训练集与测试集；应按内容指纹分组后整体划分，防止数据泄漏。

每条 JD 由两名标注员独立标注，冲突由第三人裁决。标注字段：

- 数据质量：是否相关、是否重复、发布时间、来源、公司。
- 岗位：原始名称、标准岗位名、岗位类别、级别。
- 岗位定义：核心职责、典型行业场景。
- 技能：标准技能名、原文片段、必备/加分、技能别名。
- 演化类别：新岗位、能力变更、无变化。
- 变更内容：新增、删除、修改的技能及证据。

建议再准备 30 条只用于开发调试的数据，不进入 120 条正式盲测集。

### 3.2 简历金标准集

准备 30 份脱敏简历：PDF 12 份、DOCX 12 份、TXT 3 份、扫描 PDF 3 份；覆盖单页/多页、中英文混排、表格布局、技能别名、项目描述和无技能简历。

人工标注姓名、学历、工作年限、目标岗位、技能、项目经历。扫描 PDF 若产品明确不支持，应验证系统给出可理解的“不支持/OCR 未启用”提示，不得无限转圈，也不得伪造解析结果。

### 3.3 匹配金标准集

从 30 份简历和至少 10 个标准岗位中构造 100 个“简历-岗位”样本对。由至少两名具备招聘或技术背景的评审独立标注：

- 最匹配岗位（用于 Top-1 Accuracy）。
- 可接受岗位集合（用于 Top-3 Accuracy）。
- 必备技能缺口、优势技能和不应推荐技能。
- 匹配等级：高/中/低。

若评审对最匹配岗位不一致，第三人裁决；无法形成共识的样本不进入正式测试集。

### 3.4 闭环专用批次

准备三个顺序执行、来源 ID 唯一的固定批次：

1. 基线批次：已有岗位及已有技能，用于建立初始图谱。
2. 变化批次：Java 岗位新增 RAG 等稳定技能，用于触发“能力变更”。
3. 新岗位批次：至少 2 家企业、3 条 JD、2 项稳定技能的“具身智能工程师”，用于触发“新岗位”。

另准备重复批次、单企业新标题、只有 1 项技能的新标题、完全无变化批次，用于验证阈值和幂等性。

## 4. 指标计算

### 4.1 JD 解析

岗位名称、职责、场景、技能分别计算 Precision、Recall、F1；技能别名标准化后再比对。总指标采用所有实体的 micro-F1：

```text
Precision = TP / (TP + FP)
Recall    = TP / (TP + FN)
F1        = 2 * Precision * Recall / (Precision + Recall)
```

验收标准：JD 技能与岗位字段总体 micro-F1 `>= 0.90`，并单列各字段结果；不能只报“120 条中有多少条接口返回成功”。

### 4.2 简历提取

技能实体采用别名归一后的 micro-F1；姓名、学历、年限、目标岗位采用字段准确率；项目经历采用关键要素 F1。

主验收指标为技能实体 micro-F1 `>= 0.90`，同时要求支持格式的文件解析成功率 `>= 95%`，所有失败均返回明确错误状态。

### 4.3 人岗匹配

```text
Top-1 Accuracy = 最优推荐岗位与专家金标准一致的简历数 / 简历总数
Top-3 Accuracy = 专家可接受岗位出现在前三推荐中的简历数 / 简历总数
```

主验收指标 Top-1 Accuracy `>= 0.90`。同时报告 Top-3 Accuracy、技能缺口 micro-F1，并按岗位类别给出混淆矩阵。固定写死的岗位结果、根据测试标签反推结果均判定无效。

### 4.4 新岗位与能力变更

对三分类“新岗位/能力变更/无变化”报告混淆矩阵、各类 Precision/Recall/F1 和 macro-F1。建议门槛：macro-F1 `>= 0.90`，新岗位 Recall `>= 0.90`，误报率 `<= 5%`。

## 6. 端到端验收步骤

正式演示前使用全新数据库或独立测试目录，保存每一步响应和图谱快照：

1. 启动后端和前端，验证 `/health`。
2. 上传基线批次，确认旧岗位进入图谱且没有待审核误报。
3. 上传变化批次，确认系统生成“能力变更”，图谱此时尚未变化。
4. 在审核页打开证据、批准变更，确认审核项消失且全景/技能反查图谱同步更新。
5. 上传新岗位批次，确认生成“新岗位发现”而不是旧岗位变更。
6. 批准新岗位，确认岗位注册、岗位定义、两个图谱视图和演化展示均更新。
7. 原样重复上传两个批次，确认没有重复审核、重复节点或重复关系。
8. 上传一份与目标岗位差距明显的简历，检查抽取结果；选择岗位后验证匹配分数、缺口和学习路径。
9. 修改简历技能后重新匹配，确认结果随输入变化。
10. 断开后端再操作一次，确认前端停止加载并显示错误，然后恢复后端完成重试。

闭环通过标准：上述步骤全部通过，且每次批准操作都能从“输入 JD -> 审核记录 -> 数据库状态 -> 图谱增量 -> 页面展示”追溯完整证据。

## 7. 自动化与执行命令

先补齐并锁定测试依赖，建议将 `httpx2`、`coverage` 写入开发依赖文件。之后执行：

```bash
cd "/Volumes/Extreme Pro/挑战杯/Chanllenge-Cup"
source .venv/bin/activate

python -m unittest discover -s tests -v
coverage run --source=backend,src -m unittest discover -s tests
coverage report -m --fail-under=60
coverage html

cd frontend
npm run build
```

JD解析正式评测入口已经实现。系统预测文件必须覆盖Ground Truth中的全部`evaluation_id`，正式模式会拒绝未复核标签、未批准别名、重复ID和预测覆盖不完整：

```bash
python -m src.evaluation.evaluate_jd_predictions \
  --ground-truth data/evaluation/jd_ground_truth_normalized_120_v1.jsonl \
  --predictions output/evaluation/jd_predictions_120.jsonl \
  --ontology-dir data/evaluation/ontology \
  --ontology-version v1 \
  --output output/evaluation/jd_evaluation_report.json \
  --threshold 0.90
```

人工复核完成前只能使用开发模式联调，开发模式结果不得作为正式成绩：

```bash
python -m src.evaluation.evaluate_jd_predictions \
  --predictions output/evaluation/jd_predictions_120.jsonl \
  --allow-draft \
  --allow-pending-aliases \
  --no-fail
```

后续简历与匹配评测入口：

```bash
python -m evaluation.evaluate_resume --manifest data/evaluation/resume_gold.jsonl
python -m evaluation.evaluate_match --gold data/evaluation/match_gold_100.jsonl
```

持续集成必须阻止以下情况合并：单元测试失败、覆盖率低于 60%、前端构建失败、图谱出现悬空边、三项正式评测任一低于 90%。

## 8. 测试报告模板

每次正式测试记录：代码 commit、数据集版本和 SHA-256、运行环境、执行时间、通过/失败数量、三项准确率、覆盖率、性能结果、失败样本及修复结论。

最终报告至少包含：

| 指标 | 样本量 | 结果 | 门槛 | 是否通过 |
|---|---:|---:|---:|---|
| JD 解析 micro-F1 | 120 JD | 待测 | 90% | 待测 |
| 简历技能提取 micro-F1 | 30 份 | 待测 | 90% | 待测 |
| 匹配 Top-1 Accuracy | 100 对 | 待测 | 90% | 待测 |
| 新岗位/变更三分类 macro-F1 | 120 JD | 待测 | 90% | 待测 |
| 后端与处理模块覆盖率 | 全部单测 | 待测 | 60% | 待测 |
| P0 功能用例通过率 | 全部 P0 | 待测 | 100% | 待测 |

禁止在没有金标准和计算明细时直接填写“准确率 90%”。未达标时应附错误类型分布，例如技能漏提、别名误归一、新岗位误报、匹配排序错误，并用失败样本驱动下一轮修复。
