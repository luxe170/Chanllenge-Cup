# LLM JD 提取解析模块设计

## 目标

将招聘 JD 原文转化为岗位能力图谱、岗位演化分析和审核流程可使用的结构化数据。LLM 在本模块中承担语义理解、候选抽取和证据定位职责；系统承担字段校验、归一化、置信度约束、去重、版本留痕和人工审核流转职责。

本模块不把 LLM 输出直接视为事实。所有会影响图谱结构、岗位标准库或评测结果的内容，都必须保留原文证据，并经过规则校验或人工审核。

## 适用输入

- 单条 JD 原文。
- 多平台采集后的 JD JSON 记录。
- 批量 JD 文件。
- 已清洗但未结构化抽取的岗位文本。

输入至少应包含岗位标题和正文。若存在公司、来源平台、发布时间、岗位地点、招聘类型等元数据，应一并提供给 LLM，作为判断上下文和证据链来源。

## 核心功能

### 基础字段抽取

识别 JD 中的显式字段：

- 公司名称。
- 原始岗位名称。
- 工作地点。
- 招聘类型。
- 学历要求。
- 工作年限或经验要求。
- 发布时间。
- 薪资、实习周期或到岗要求。
- 来源平台和原始链接。

这部分应优先使用原始结构化字段，LLM 只用于补齐、修正格式混乱或正文中隐藏的信息。

### 岗位标准化

判断原始岗位名称与标准岗位库之间的关系：

- 可归入已有标准岗位。
- 与多个已有岗位相似，需要人工审核。
- 无法归入已有岗位，进入新岗位候选。
- 明显不属于目标赛题范围，应标记为边界或剔除。

LLM 输出应包含标准岗位建议、相似岗位列表、差异说明、证据片段和置信度。系统不能只根据岗位名称相似度自动合并岗位，尤其是新兴岗位、交叉岗位和泛 AI 岗位。

### 技能抽取

从职责、任职要求和加分项中抽取技能实体：

- 编程语言。
- 框架和工具。
- 算法与模型能力。
- 工程化能力。
- 数据与平台能力。
- 业务场景能力。
- 安全、测试、部署和运维能力。

每个技能应包含原始表达、标准技能建议、必备或加分判断、证据片段、来源段落、置信度和重要度。LLM 应区分“岗位真的要求该技能”和“只是业务背景中提到该技能”。

### 技能归一化候选

将同义、别名和中英文混写技能归并到标准技能库：

- 大模型、LLM、大语言模型。
- K8s、Kubernetes、容器编排。
- 检索增强生成、RAG、向量检索。
- 智能体、Agent、Multi-agent。

对无法归一到已有技能库的技能，输出为待审核新技能候选。新技能候选应包括建议名称、别名、所属技能簇、出现证据和推荐理由。

### 职责与业务场景抽取

抽取岗位职责和典型业务场景：

- 核心工作内容。
- 技术落地场景。
- 业务对象。
- 协作对象。
- 产出形式。
- 对候选人的能力要求。

职责和场景不应与技能混淆。技能描述“会什么”，职责描述“做什么”，场景描述“在哪里做、解决什么问题”。

### 新岗位发现辅助

当 JD 不能稳定归入已有岗位库时，LLM 生成新岗位候选说明：

- 建议岗位名称。
- 与已有岗位的相似点。
- 与已有岗位的差异点。
- 核心技能组合。
- 支撑该判断的 JD 证据。
- 是否需要进入人工审核。

最终新岗位判定应综合企业数量、样本数量、时间窗口、技能组合一致性和人工审核结果，而不是只依赖 LLM 判断。

## 输出要求

输出应是结构化结果，至少覆盖：

- 原始记录 ID。
- 岗位标准化结果。
- 技能抽取结果。
- 职责列表。
- 场景列表。
- 是否边界样本。
- 是否新岗位候选。
- 证据片段。
- 置信度。
- LLM 模型名称、提示词版本和生成时间。

所有字段必须可以追溯到原文。没有证据的结论应标记为低置信度或不输出。

## 人工审核边界

以下结果必须进入审核：

- 新岗位候选。
- 新技能候选。
- 岗位归一化置信度较低。
- 一个 JD 同时匹配多个标准岗位。
- 技能是否必备存在歧义。
- JD 文本疑似非目标岗位、营销岗位或运营岗位。

审核人员应能看到 LLM 结论、置信度、原文证据、相似项对比和系统规则判断。

## 质量指标

建议评估：

- 岗位标准化准确率。
- 技能实体 Precision、Recall、F1。
- 必备/加分分类准确率。
- 新岗位候选召回率。
- 边界样本识别准确率。
- 证据片段命中率。

正式评测必须使用人工确认的金标准，不能使用 LLM 自生成标签作为唯一答案。

## 后续接入建议

优先做离线批处理能力，将 LLM 结果写入独立增强数据文件，再由后端按“LLM 增强结果、规则结果、实时数据、演示数据”的顺序读取。在线页面不应在用户打开时同步等待 LLM。
